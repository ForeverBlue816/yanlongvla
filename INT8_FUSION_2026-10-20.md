# INT8 kernel-fusion track for π₀.₅ W2A8 (2026-10-20), 5-day cap

User instruction, recorded verbatim (2026-10-20):

Goal: turn the INT8 path into a real speed-up on the RTX 6000 Ada / L40S by fusing the small kernels that currently cancel the INT8 GEMM gain. Current numbers: prefill 52.2 ms (BF16 52.4), expert 4.12 ms/step (BF16 3.41), end-to-end 0.87–0.95×. Accuracy parity must be preserved at every step (max |ΔA| vs the fake-quant W2A8 path ≤ 1e-3 on 256 observations).

## Day 1 — measure before touching anything
1. nsys/Nsight Compute profile of one BF16 inference and one W2A8 inference (CUDA graphs on). Produce a per-kernel-class time table for prefill and for one expert step: GEMM, attention, RMSNorm, Hadamard, activation quantize, dequant/scale epilogue, SwiGLU/GELU, residual add, embedding/misc, launch gaps.
2. Compute the lower bound: time of INT8 GEMMs alone (cuBLASLt, prefill shapes at ~800 tokens; expert shapes at M = 10). This is the best any fusion can reach; report it next to the current totals.
3. Count kernel launches per prefill and per expert step for BF16 and W2A8.

## Day 2–3 — prefill (compute-bound): fuse around the GEMM
F1. One Triton kernel for RMSNorm → Hadamard → per-token absmax → INT8 cast, writing INT8 activations plus the per-token scale. Replaces 3–4 kernels per linear input.
F2. INT8 GEMM with fused epilogue: cuBLASLt (CUBLASLT_EPILOGUE_*) or CUTLASS so that per-row weight scale × per-token activation scale, bias and the residual add happen inside the GEMM; no separate dequant kernel. Output BF16.
F3. Fuse projections that share an input: Q/K/V as one GEMM (N = concatenated), gate/up of the MLP as one GEMM followed by a fused SwiGLU kernel.
F4. Attention stays BF16 (FlashAttention); vision encoder gets the same F1–F3 treatment, since it is part of the 52 ms.
F5. Re-capture the whole prefill as a single CUDA graph.
Target: prefill ≤ 0.75× BF16 (≈ 39 ms). Report the kernel-class table again after each fusion so the gain is attributable.

## Day 4 — expert (launch-bound at M = 10)
E1. Fuse RMSNorm + precomputed modulation table (scale/shift) + Hadamard + INT8 cast into one kernel per linear input.
E2. Fused Q/K/V GEMM and fused gate/up GEMM + SwiGLU as above; cross-attention over the cached prefix K/V stays BF16.
E3. One CUDA graph for the entire 10-step loop (and a 2-step variant), not per step.
E4. Only if E1–E3 still leave the expert slower than BF16: INT8-resident weights for the expert with a persistent-kernel "megakernel" that runs a whole layer per launch (Triton/CUTLASS). Skip if not feasible in a day.
Target: expert ≤ BF16 per step (≤ 3.4 ms); stretch 2.5 ms.

## Day 5 — parity, measurement, report
- Parity on 256 observations vs fake-quant W2A8; LIBERO screening 200 episodes with the fused path (expect identical to within noise).
- Latency table (median and p95 of 100 warm inferences, batch 1, CUDA graphs): BF16 10/2 steps; W2A8 before fusion; W2A8 after fusion; INT8-GEMM-only lower bound. Columns: prefill, expert/step, end-to-end, peak and resident memory, kernel launches.
- One paragraph on what remains between fused W2A8 and the GEMM-only bound.

## Stop rules
- Any fusion that breaks parity (> 1e-3) is reverted, not tuned around.
- If after Day 3 prefill is not below 0.9× BF16, stop prefill work and report the kernel-class table as the explanation.
- Hard stop end of Day 5 regardless of outcome; the paper's efficiency table uses whatever is measured by then, honestly labelled.

## Schedule and implementation notes (agent)

Day 1 = 2026-10-20, hard stop end of 2026-10-24. Tooling: nsys/Nsight Compute are not installed on the cluster; the kernel trace comes from torch.profiler (CUPTI) over CUDA-graph replays, which records every kernel inside the graph with device timing; launch gaps = replay wall time − summed kernel time. Scripts: `plustrain_int8_day1.py` (kernel-class tables, launch counts, INT8-GEMM-only bound from the hooked real shapes), fusions in `plustrain_int8_runtime.py` (Triton kernels; each fusion gated by the 256-observation parity check in `plustrain_int8.py --stage parity`), latency from `plustrain_int8_bench.py`. GPUs: the GR00T 2-bit rows keep priority on the 6000 Ada; fusion profiling/parity jobs are short (≤ 1 h) and run on any free Ada GPU; the Day-5 table is measured on one GPU model, every row on the same model.
