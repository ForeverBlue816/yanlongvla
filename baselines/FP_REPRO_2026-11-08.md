## Gaps: protocol differences seen in code, and unknowns

### Fractal (mean -4.3 pp; open_drawer 48 vs 65)
Our command equals the README command in model, embodiment tag, wrapper, n-action-steps, n-envs, max steps (simpler/s5.sh vs README lines 124-130). Differences:
1. We pass --seed 7. In rollout_policy.py lines 302-307, a seed only sets env seeds 7..11 for the FIRST reset of the 5 envs. Later autoresets are unseeded. Official runs are unseeded (seed=None). Effect: small, only the first 5 episodes.
2. We pass --n-episodes 100 in one call; the README shows 10 per call. How NVIDIA got 100 (10 calls? different seeds each?) is UNKNOWN.
3. Attention kernel: README of ours says SDPA; flash-attn run gave open_drawer 50/100 (RIGOUR R5). Tested, not the cause. Dtype of inference not compared (UNKNOWN for the card).
4. We record videos (--video-dir). Official default also sets a video dir to /tmp (rollout_policy.py lines 565-567), so same.
5. env name google_robot_open_drawer maps to OpenDrawerCustomInScene-v0 (random top/middle/bottom drawer; SimplerEnv simpler_env/__init__.py). The card does not say which drawer set; same name as ours.
6. Not stated by NVIDIA: checkpoint revision, GPU and driver, SAPIEN renderer, SimplerEnv commit, number of seeds. UNKNOWN.
7. terminate_on_success defaults False (rollout_policy.py line 95), so every episode runs the full 300 steps; completion-order bias with 5 envs is therefore small.

### Bridge stack_cube (30% vs 48%)
1. Layouts. The official WidowXBridgeEnv.reset ignores seed/options (simpler_env.py reset: only env.reset(seed)), so layouts are drawn at random; with unseeded runs the draw is not even. We enumerate all 24 layouts evenly (k mod 24). The mentor's note: FP fails layouts 11 to 23 of stack_cube (RIGOUR H2). If the official random draw is not uniform over layouts, or if the card used a different layout set, the rate differs. UNKNOWN which.
2. Envs: official 5 async envs, ours 1 sync env. Does not change policy outputs in principle.
3. Seeds: official unseeded policy noise (flow-matching noise from the global torch RNG); ours torch.manual_seed per episode. Spread of an unseeded 100-episode run is unknown (B1 plans 3 repeats).
4. n-action-steps 4, max steps 300: same. Success rule: official ORs success over steps (rollout_policy.py lines 320-348); ours any step success: same.
5. Episode count: 100 vs 120 (SE 5.0 vs 4.2).
6. Checkpoint: the README numbers may come from an earlier N1.7 training run than the released revision 940134b. UNKNOWN. Also SimplerEnv commit and render settings UNKNOWN.
7. Attention kernel: SDPA vs flash-attn not tested on Bridge. UNKNOWN.

### Most likely causes per gap (with evidence)
Fractal open_drawer / mean:
1. Layout and variant draw of drawer tasks (random drawer pose, brightness, texture) plus unseeded noise: 4 reruns give 48-53, never 65 (RIGOUR E6), so it is not run-to-run noise but may be a different drawer set or env version. Evidence: drawer env draws from RNG; card gives no variant.
2. Card ran another checkpoint revision, SimplerEnv commit or render setup. Evidence: only the drawers and none of the pick tasks differ; SDPA test excluded the kernel.
3. Inference precision or other server setting (dtype, flash-attn); weak, since flash-attn gave 50.
Bridge stack_cube:
1. Layout sampling: seeded even enumeration vs random unseeded draw (code: official reset drops seed and options). QTIP solves 72/120 on layouts that FP fails, so FP is on a decision boundary there.
2. Sensitivity of FP to tiny numeric changes (H4: one noise draw moves stack_cube 4-12 episodes) so the official 48 may be a lucky unseeded run; official spread UNKNOWN.
3. Different checkpoint or environment version behind the README table; evidence only that README numbers are "from default SimplerEnv evaluation runs" with no revision.
