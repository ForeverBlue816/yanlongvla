GR00T N1.7 2-bit quantization baselines: progress report for the mentor

Status on 9 Nov 2026, 22:45 (UTC+8). Models: GR00T N1.7 on LIBERO-Plus, SimplerEnv-Bridge and SimplerEnv-Fractal. A short pi0.5 note is in section 2.
Code and evidence: pull request #5 (branch baselines-nov9-shrink-fp-repro). Each item below has a "Code and evidence" line with file links.
All numbers come from complete runs with a .done file. Runs that are still active are marked "running".

1. Summary

  1. LIBERO-Plus: our FP equals your FP (618 of 1000). Every 2-bit method is below FP. QTIP is the best (573). AQLM is the worst (401).
  2. Bridge is the opposite. QTIP, QuIP#, VPTQ and AQLM are at or above FP (total of 840 episodes: FP 503, 2-bit rows 527 to 565). The gains come from two tasks, carrot_on_plate and stack_cube.
  3. A plain weight shrink gives the same gain. FP weights × 0.95, with no quantizer, get 587 of 840 and are the best Bridge row. So the Bridge result is no evidence that quantization helps.
  4. The 2-bit error does not work as a shrink. On real inputs, it shrinks the layer outputs by only 0.2 to 0.9%. The part of the error that is not a shrink gives the gain alone. We do not yet know why.
  5. Our FP matches NVIDIA's FP on Bridge when we use NVIDIA's command (61.5% against 62.3%). The stack_cube difference (30% against 48%) is solved. NVIDIA's command always walks the same fixed list of start layouts (seed 2022), and the list has many easy layouts. With a new list for each run, the same command gives 33.8%.
  6. Fractal open_drawer is not solved. Ours is 48 to 58 of 100 (54.2% over 500 episodes). NVIDIA reports 65. We ruled out seed, attention kernel, checkpoint version and library versions. Question for the mentor (A20).
  7. Runs were not bit-identical because the env keeps state between episodes. We found the cause. With a new env for each episode, repeated runs are identical.
  8. Branch F (section 4) lists the decisions that we need from the mentor.

A. Does our FP match NVIDIA's FP?

A1. Bridge stack_cube: ours 30%, NVIDIA 48%  ANSWERED

Question
Under the mentor's seeded protocol, our FP gets 30% on stack_cube. NVIDIA reports 48%. Why?
How
  1. We ran NVIDIA's own command on our stack (5 envs, 100 episodes, no seed). Mean of 7 tasks: 61.5% against 62.3% (H6). Every task is within 4 points.
  2. We changed one factor at a time: attention kernel, seed, number of envs, server batch size, episodes dropped at the end of a run (X19, X20). We made 12 repeats of NVIDIA's command and 10 seeded runs.
  3. We read the env code and classified the layout of all 1200 official episodes from the first video frame (X22). The classifier is exact on 120 of 120 known frames.
  4. We pre-registered H9 before the runs: NVIDIA's command with a different seed for each run (6 × 100 episodes). Prediction: about 33 to 41%, not 47%.

B. Why are the 2-bit rows above FP on Bridge?

B1. Is it random noise?  ANSWERED: no

Question
Does any small random change to the weights raise carrot and stack_cube?
How
H4 and H5: Gaussian noise (2% and 6% of each weight's rms, about the size of the 2-bit error at the layer output) on the same 432 weights. 6 draws at 6%. FP is exactly reproducible (H3), so a change is an effect of the weights.
Result
One draw moves a task by up to 16 episodes, in either direction. No draw raised both tasks by 10 or more. Every 2-bit row's stack_cube gain (+26 to +45) is above every draw. This is a weak test: 6 draws give about 1 chance in 7 per row.
Code and evidence
Noise builder: groot/perturb.py. Tests H3 to H5 and readings: RIGOUR_2026-11-06.md.
Status
Random noise does not copy the gain. H4 closed as "mixed". Later tests (B2, B4) are stronger.

How

B4. Do the 2-bit rows work through the shrink?  OPEN

Question
If a shrink gives the gain, and the 2-bit error contains a shrink, is that shrink the reason for the 2-bit gain?
How
  1. X25 (CPU): we measured the shrink in activation space with the stored Hessians (calibration and held-out). It uses tr(E H Wᵀ) / tr(W H Wᵀ) for each of the 432 tensors.
  2. X15 orth: FP + (QuIP# error minus its weight-space shrink), 7 tasks.
  3. X26 mxorq: 0.95 × orth. This also removes the +5% output gain that orth has.
Result
  • In weight space, the shrink is -0.05. On real inputs, the QuIP# error shrinks the layer outputs by only 0.2 to 0.9%. The shrink is mostly in directions that the inputs seldom use. Calibration and held-out Hessians agree (within 0.004).
  • The orth row makes the outputs about 5% larger.

E. Are our measurements stable and fair?

E1. Why were repeated runs not identical (A12, X3)?  ANSWERED

Question
FP run twice with the same seed gave the same result on 809 of 840 episodes. Basket and the drawers flipped (24 episodes). Runs with --no-env-termination differed before the first success. Why?
How
The step logs showed that episodes 0 and 1 never differ, and that a difference depends on how the previous episode ended (Fisher p = 0.006 carrot, 0.003 stack). Test: --fresh-env (a new env for every episode); two FP runs and one run with --no-env-termination, on carrot and basket.
Result
With a fresh env, two runs are bit-identical: all 120 step logs on carrot and on basket. The no-termination run equals them on every step before the first success (0 of 120 episodes differ). Against the old protocol, 71 of 120 carrot episodes differ (34 flips), but the totals are the same (75 and 75; basket 58 and 56).
Code and evidence
New-env option: --fresh-env (used at line 146). Rows fe1, fe2, fent1: s5.sh. Divergence analysis: explore_reports/l2/x3_diverge.py, explore_reports/l1/S7_A11_A12.md. Runs X3, A12: EXPLORE_2026-11-08.md.
Status
The cause is state that carries over between episodes (PhysX or renderer; the reset does not clear it). A12 and the X3 caveat are closed.
Next
Decision for the mentor: keep the old protocol (as in the tables) or re-run key rows with --fresh-env? Totals did not move on the 2 tasks tested.

E4. VPTQ: lower layer error, fewer successes (S5)  ANSWERED

Result
